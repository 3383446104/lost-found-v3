## 时间衰减失效修复 + 参数调温和（用户说"要放入新日期物品测试"→ 先修前提）

用户准备发布**新日期物品**做测试 → 我指出关键前提：**当前时间衰减失效**（days_old 恒 0），
不修的话新老物品分数不会有差异，**测不出东西**。遂按上一轮推荐的温和方案修复。

### 根因（「静默失败」家族又一例）
- `api/items.py` / `services/match_service.py` 各自 `try/except` 解析 `created_at`：
  `datetime.fromisoformat("2026-07-02 01:06:44")` **解析成功但返回 naive** →
  与 aware 的 `datetime.now(timezone.utc)` 相减抛 **TypeError** → 被 `except Exception` 吞成
  `days_old = 0` → **衰减恒 ×1.0**，且**无任何日志**，外部完全无法察觉。
- SQLite `CURRENT_TIMESTAMP` 存 UTC 但不带时区标记 —— 这是触发条件。

### 修法（一处修好、两处受益、可测）
- 新增公共函数 **`app/utils/time_utils.days_since_utc(time_value, *, now=None)`**：
  统一处理 ISO（含 Z/偏移）、SQLite 空格格式（含微秒）、naive→补 UTC；解析失败返回 0 **并记 warning**。
- 两个调用点改用它，删除各自的 try/except 兜底。
- 新增 **`tests/test_time_decay.py`（5 例）**：核心守卫「SQLite 无时区格式必须算出真实天数（而非 0）」
  + ISO 三形态/微秒/未来/非法 + 乘数符合配置 + **集成断言「days_old 增大 → 分数必须下降」**。
- 参数调温和（用户确认）：`MATCH_DECAY_DAYS` 90→**240**、`MATCH_DECAY_FLOOR` 0.2→**0.6**。
  原因：原 90/0.2 过激，76 天物品被打到 12%，配合 0.35 阈值会让**结果集体消失**；
  温和档下老物品 38% **仍可见 → 无需改动阈值体系**（这是选温和档的关键理由）。

- 测试：213 → **218 用例 / 216 passed / 2 门控 skip / 0 failed**。

## 【重大】打分口径重构：按查询形态分三种检索模式（用户决策 + 实施，提交 96216f1）

用户实测「拿原图匹配只有 52%」并判断「**算法思想有问题**」→ 经四轮澄清（他前两次表述我理解偏了），
最终确认需求：**按查询形态分三种检索模式** —— ①文字检索 ②图片检索 ③图文混合检索，各自独立打分。

### 实验证据（量化证明用户的判断）
评测集 78 有效对的正负样本分布重叠：
- 单通道：跨模态 **0.067** / 文-文 **0.158**
- **混合综合分：0.397（2.5~6 倍恶化）** ← 这就是 AUTO/EMAIL 阈值长期「结构性无解」的机制性原因
- **结论：不是样本不够，是尺子错了**（把三种异质相似度等权平均）

### 实现（巧妙点：零分支代码）
1. **权重改「主证据 + 辅助证据」**：同模态（文-文/图-图）各 **0.75**、跨模态 **0.25**。
   配合既有「缺通道动态归一化」，三种模式**自动成形**：
   文字检索 → 0.75/0.25；图片检索 → 0.75/0.25；图文混合 → 0.43/0.43/0.14。**不需要任何 if 分支**。
2. **跨模态尺度映射** `_map_cross()`：原生余弦（0.15~0.35）按实测分布拉伸
   （LO=0.194 负样本均值→0、HI=0.298 正样本均值→1）。**仅作用外层加权与展示**，
   阶段5 惩罚仍用原始值（其阈值按原始尺度设计）。
3. **惩罚触发条件收窄**：仅「文-文高 **且** 图-图不高」（真·文本撞车）。
   原 `max(图-图, 文-文)` 会误伤最可靠匹配（原图自比被无谓压低 15.6%）。
4. **三分数分离**（解决阈值尺度 vs 展示口径两种需求）：
   - `content_score`：不含类别/位置/时间 → **与标定同尺度 → 阈值判定**
   - `match_score`：含时间衰减 → 排序（新物品优先）
   - `similarity` = **最强证据通道 = 展示分**（界面与邮件）
   ⚠️ 踩坑：标定刻意不传衰减，若直接用完整分比阈值，老物品会被系统性过滤
   （实测文字强命中内容分 0.905、衰减后 0.565 < 阈值 0.625 → 结果消失）→ 故必须分离。
5. **证据链**：`level`（confirmed/high_suspect/related/reference）+ `basis` + `channels`。

### 实测效果
| 场景 | 改造前 | 改造后（展示分）| 等级 |
|---|---|---|---|
| 拿原图搜自己 | 52% | **100%** | 确定为同一物品 |
| 文字描述命中同款 | 58% | **96%** | 确定为同一物品 |
| 描述「眼镜」命中 | — | **100%** | 确定为同一物品 |

### ★ AUTO / EMAIL 阈值**首次标定成功**（此前多轮均「无解」）
| 阈值 | 建议值 | Precision | Recall |
|---|---|---|---|

Recall@1 也由 0.75 → **0.7778**（@3/@5/@10 保持 1.0）。
⚠️ 样本仍小（36 正样本；EMAIL 阈值处仅 7 个）→ 建议灰度观察后再启自动推送。

## 邮件通知未触发的排查 + 阈值尺度修复（提交 9d1fcef）

用户反馈「发布物品后邮件通知没触发」→ 逐环排查触发链。

### 排查结论（两层原因）
1. **直接原因（非 bug）**：`.env:27 AUTO_MATCH_ENABLED=false` → `match_service.py:14` 直接 return，
   不打分/不落库/不通知/不发邮件（灰度期有意设计）。
2. **隐藏缺陷（真 bug）**：`auto_match_and_notify` 用 `compute_weighted_similarity()` 的返回值
   （**含时间衰减的排序分**）比 `MATCH_THRESHOLD_AUTO/EMAIL`，而阈值标定在**内容分**尺度
   → 老物品被系统性挡住。

### 实测证据（真实库，25 组跨类型物品对）
- 「蓝牙耳机 ↔ 蓝牙耳机」真匹配对：内容分 **0.9377**（≥AUTO 0.734）/ 81 天衰减后排序分仅 **0.6278**（＜阈值）
  → **旧逻辑 0 组通过、新逻辑 2 组通过；跨类别 23 组仍正确挡掉（无误报）**。
- SMTP 配置齐备（smtp.qq.com:465 + 授权码）；历史 85 条 matches + 166 条双向通知证明机制本身完好（最近 2026-07-02）。

### 修复（提交 9d1fcef）
- `match_service` 改用 `compute_match_detail`：**判定用 content_score**、排序用 match_score、
  展示用 reference_score；邮件触发同样按 content_score。
- 通知与邮件加入**匹配等级**（高度确定/高度疑似/可能相关/仅供参考）与**命中依据**；
  `send_match_notification()` 新增 `level_text`/`basis_text` 参数。
- **测试有效性修复**：`test_qa_v350_precheck.py` 有 4 处 mock 了**旧接口名**
  `compute_weighted_similarity` → mock 全部静默失效（其中 3 处因"期望不落库"侥幸通过）。
  全部适配新接口。
- 新增 `tests/test_match_scale_consistency.py`（3 例）尺度守卫。
- 测试 226 → **229 用例 / 227 passed / 2 门控 skip / 0 failed**。

## 首页「智能查找」栏外观修复（用户截图反馈）

用户发截图要求分析外观问题 → 定位后用户说"直接改"，已修（提交 `d7099b0`）。

### 根因（Element Plus 用法陷阱）
`el-input` 的 **`#append` 插槽自带浅灰背景**（`.el-input-group__append`），把
`type="primary"` 的按钮塞进去后**主色被灰底覆盖** → 全页最重要的操作看起来像
浅灰禁用态；且 append 的直角边框会抹平输入框右侧圆角 → 交界处视觉断层。
（`HomeView.vue` 的智能查找入口即此写法。）

### 修法（分离布局）
- 移除 `#append`，按钮提升为同级元素，包进 `.smart-bar`（flex + gap 12px）；
- `.smart-btn { flex-shrink: 0; font-weight: 600 }`；窄屏媒体查询下按钮占满整行；
- 文案精简：placeholder 由 41 字缩到「描述一下物品，例如：…」；hint 去掉与
  placeholder 重复的「用自然语言描述即可，无需纠结关键词」。

### 验证与教训
- 转译产物核对（smart-bar/smart-btn 生效、append 痕迹 0）+ 构建 ✓ 2.38s + SFC 检查 0 问题。
- ★ **可复用经验**：Element Plus 里 `#append`/`#prepend` **不是**放主按钮的地方
  （它们是有背景的附加块）。主操作应作为同级元素独立布局；只有「单位/后缀文本」
  这类无强调需求的内容才适合 append。
- ★ 环境坑：Bash 工具传含嵌套引号的 `python -c` 会被 shim 解析失败
  （`syntax error near unexpected token '('`）→ **一律写成临时 .py 文件再跑**。
