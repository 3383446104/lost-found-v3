### 项目真实规模（与文档口径不同）
- 后端：6 个路由模块、**36 个端点**（auth 6 / items 11 / admin 10 / notifications 4 / stats 1 / announcements 4）。
- 前端：**9 个路由页面**（文档写 8 个）。

### 关键缺陷（按优先级）
- **P0 禁用用户 JWT 不失效**：`dependencies/auth.py:54` 只拦 `role=='deleted'`，不拦 `disabled`；前端 `router/index.js:77` 读的是 localStorage 旧 user（`authStore.restore()` 不刷新后端）。禁用后该用户 7 天内仍可调用全部接口。
- **P0 今日统计 8 小时时区错位**：`stats.py:20` 用本地时间 `datetime.now()` 做日期前缀，SQLite `CURRENT_TIMESTAMP` 存 UTC → 北京时间 00:00–08:00 审核通过的物品被算到前一天。
- **P0 requirements.txt 缺 `bcrypt` 直接依赖**（代码 `import bcrypt`，只靠 `passlib[bcrypt]` 间接带出）；`passlib` 实际未被使用。
- **P1 颜色直方图未持久化**：`items.py:507`、`match_service.py:59` 每次匹配对每个候选重新开图解码算直方图，N 候选 = N 次磁盘 IO。
- **P1 邮件同步阻塞事件循环**：`email_utils.py` 用同步 `smtplib(timeout=10)`，在 async 端点内直接调用（`items.py:648`、`admin.py:244`）。
- **P1 路由顺序为隐性契约**：`items.py` 依赖静态路径排在 `/{item_id}` 之前，CHANGELOG Bug #4 与 #7 是同一根因，已踩两次。
- **P1 `asyncio.create_task` 被裸 `except: pass` 吞异常**：`admin.py:490/538`；`admin.py:560` 的 `count=cur.rowcount` 取值不准。
- **P2 请求体普遍裸 `dict`**（`PUT /me`、admin 多处），与已有 Pydantic v2 `models/` 风格不统一。
- **P2 死代码**：`main.py:31` `LocalhostRegexOrigin` 未使用；`main.py` 版本号 `2.0.0`；`config.CORS_ORIGINS` 未生效（实际用 `allow_origin_regex`）；`database.py:160` 仍创建 `uploads/avatars/`（头像功能 V3.3 已删）。

### 已核实事实
- 当前模型：`open_clip.create_model_and_transforms('ViT-B-32', pretrained='laion2b_s34b_b79k')`（`clip_service.py:27-32`），tokenizer 为 `open_clip.get_tokenizer('ViT-B-32')`，**上下文上限 77 tokens**；设备默认 CPU（有 CUDA 才用）。
- **架构关键点**：`compute_weighted_similarity` 只算 **img·img、text·text、color·color** 三个自相似度，**从不做 img·text 跨模态对比** → CLIP 的图文对齐能力在本项目里根本没被用到。文本通道本质是「两段中文描述的语义相似度」。
- **分词实测（用项目 venv 跑通，不依赖权重）**：中文 ≈ **2.3–3.5 token/字**，英文 ≈ 0.22 token/字符。
  - 「黑色钱包」4 字 → 14 tokens
  - 33 字典型描述 → **77（触顶）**
  - 71 字较长描述 → **77（严重截断）**
  - 44 字分类枚举 → 76
  - 107 字符英文同义句 → **24**
  → **典型中文物品描述就已经触及 77 上限，描述后半段被静默丢弃**。
- **open_clip 实测**：`list_pretrained()` 共 121 条，**含 cn/chinese/zh 的条目为 0** → open_clip 无法加载 Chinese-CLIP。但内置两个多语言文本塔变体：`xlm-roberta-base-ViT-B-32`(laion5b_s13b_b90k)、`xlm-roberta-large-ViT-H-14`(frozen_laion5b_s13b_b90k)。
- **Chinese-CLIP（OFA-Sys，~2 亿中文图文对）**：5 个规模 RN50 / **ViT-B/16**(188M) / ViT-L/14(406M) / ViT-L/14@336 / ViT-H/14；**无 ViT-B/32 变体**，最小 ViT 是 B/16（patch 49→196，CPU 编码更慢）；不在 open_clip 内，需 `pip install cn_clip`（`load_from_name`）或 HF `transformers` 的 `ChineseCLIPModel`；MUGE zero-shot R@1 **63.0** vs Wukong 42.7 / R2D2 49.5。
- 依赖现状：`requirements.txt` **无 transformers、无 cn_clip**；`huggingface_hub` 是 open_clip 的传递依赖。
- 权重缓存：`~/.cache/huggingface/hub/models--laion--CLIP-ViT-B-32-laion2B-s34B-b79K` 只有空 ref/blobs/snapshots，`~/.cache/clip` 为空 → **真实权重本地未下载**，做真实相似度实验需下载约 600MB。

### 分析结论（供后续复用）
- 文本通道确实有真实缺陷（截断 + 分布外），且不只是「权重 0.30」那么轻——阶段 5 的腰斩条件 `img_sim>0.7 且 text_sim<0.15` 是按英文分数分布标定的，中文输入下阈值语义不可靠。
- 但因架构是 text·text，**换中文句向量模型（如 BAAI/bge-small-zh-v1.5，约 95MB、512 维、CPU 友好）比换整个 CLIP 更对症、更便宜**。
- 若坚持单模型统一：Chinese-CLIP ViT-B/16 是对的选择；折中且零新依赖的是 open_clip 的 `xlm-roberta-base-ViT-B-32`（同 open_clip API，仅改模型名字符串）。
- **任何模型替换都必然伴随**：① 全部 `items.image_vector`/`text_vector` 需重算（JSON TEXT 存储，维度变化不影响 schema，但嵌入空间变了必须全量重嵌入）② 阈值 0.20/0.65/0.75 需重新标定 ③ 需要一份带标注的评测集来量化（也是答辩加分点）。好消息：`conftest.py` 已打桩 `get_image_feature`/`get_text_feature`/`get_color_histogram`，**72 条测试基本不受影响**。

### 补充结论（用户强调「项目只面向国内、全中文提示词」之后）
- **换模型只修到 30% 的流水线**：img·img(0.50) 的图像本身不含语言 → 换中文模型收益低；color·color(0.20) 手工 RGB 直方图 → 收益为零；只有 text·text(0.30) 真正受益（截断消失 + 中文语义）。而迁移成本（重嵌入 + 阈值重标定 + 新依赖）是对整条流水线的。
- **最锋利的论点**：CLIP 文本塔（含 Chinese-CLIP 的文本塔）是为「图文对齐」训练的，把它用于 **text·text 相似度**本身就是次优用法；而 bge/text2vec 这类中文句向量模型正是用文本对（STS/NLI）对比学习训练的 → **对 text·text 这个子任务，中文句向量模型严格优于任何 CLIP 文本塔**。
- **决定性分叉（已问用户，已答）**：未来是否要支持「用文字描述搜物品」(text→image)？
  - **用户答复：要保留这个可能** → 走 **CLIP 路线**（中文句向量模型出局，因为它无法与图像向量对齐）。
  - 推荐目标：**Chinese-CLIP ViT-B/16**（原生中文 + 中文 char-level tokenizer 消除 77 截断 + 基准 MUGE R@1 63.0 + 自带 text→image 能力）；`open_clip` 内置的 `xlm-roberta-base-ViT-B-32` 可作「零新依赖」的先手验证。
  - 换过去顺带解锁两件现有架构做不到的事：① 真正的「文→图」检索（现在是 text·text 凑的）② 阶段5 交叉校验可从「两个自相似度比大小」升级为**真正的跨模态一致性校验** cos(query_text, target_img)。
- 附带事实：中文 BERT 系 tokenizer 对中文近似 **1 字 ≈ 1 token、上下文 512** → 换任何中文文本编码器都能立刻消除 77 截断问题。

### 补充结论 2（用户否决 ViT-B/16：「模型太小了」）→ 档位升级
- **官方实测指标（已联网核实，来源 OFA-Sys/Chinese-CLIP README + sotaverified）**：

| 规格 | 参数量 | 视觉塔 | 文本塔 | 分辨率 | MUGE 平均召回 | COCO-CN R@1 | Flickr30k-CN R@1 |
|---|---|---|---|---|---|---|---|
| RN50 | 77M | ResNet50 38M | RBT3 39M | 224 | 69.2 | 66.8 | 66.7 |
| ViT-B/16 | 188M | ViT-B/16 86M | RoBERTa-wwm-Base 102M | 224 | 77.4 | 77.0 | 79.1 |
| **ViT-L/14** | **406M** | ViT-L/14 304M | RoBERTa-wwm-Base 102M | 224 | **80.1** | 78.9 | 82.7 |
| ViT-L/14@336px | 407M | ViT-L/14 304M | RoBERTa-wwm-Base 102M | 336 | 81.3 | 80.1 | 84.4 |
| ViT-H/14 | 958M | ViT-H/14 632M | RoBERTa-wwm-Large 326M | 224 | 83.6 | 81.5 | 83.8 |

- **视觉算力相对估算（patches × layers × dim²，相对现役 ViT-B-32 的倍率）**：B/16 ≈ 4.0×；L/14 ≈ 18.6×；L/14@336 ≈ 41.8×；H/14 ≈ 38.7×。相对 B/16：L/14 4.6×、@336 10.4×、H/14 9.7×（H/14 虽大但跑 224，patch 数与 L/14 相同）。
- **关键不变式**：Chinese-CLIP 五档投影维度统一 **512** → SQLite 存储格式（BLOB/TEXT）不变，但**全量重嵌入**不可省（换空间后新旧向量不可比）。
- **CPU 成本真相**：图编码只在「发布/上传物品」时发生一次；**检索路径只编码文字**（RoBERTa-Base 单条 query 约几十 ms）。所以换大模型拖慢的是录入，不是查询。
- **@336 对本场景的额外理由**：失物（钥匙/校园卡/耳机盒）在照片中占比小，336px 输入对小目标有利，MUGE 的 +1.2 低估了实际收益。
- **集成路径（本次唯一新依赖）**：open_clip 无 Chinese-CLIP 条目 → 走 `pip install cn_clip`（`load_from_name`）或 HF `transformers` 的 `ChineseCLIPModel` + `sentencepiece`。二选一需架构师定。
